# Praylist analytics event taxonomy

Version: 1
Status: approved for local implementation

Analytics is optional and privacy-first. Version 1 has no remote provider or event-payload persistence. Events are delivered only to the configured in-process client; the production default is no-op.

## Envelope allowlist

An event may contain only:

| Field | Type | Rule |
| --- | --- | --- |
| `taxonomyVersion` | integer | `1` |
| `name` | enum | One of the event names below |
| `source` | enum | `onboarding`, `today`, `widget`, `system` |
| `count` | integer | Optional; nonnegative and bounded |
| `durationBucket` | enum | Optional: `under10s`, `10to30s`, `30to60s`, `1to3m`, `over3m` |
| `status` | enum | Optional: `started`, `completed`, `skipped`, `granted`, `denied`, `restricted`, `success`, `failure` |
| `timestamp` | ISO-8601 date | Required; generated by the app |

No arbitrary dictionary, string, identifier, user ID, or nested payload is part of this contract. Unknown names or fields are rejected. The strongly typed implementation is the authoritative validation boundary.

## Version 1 event names

| Event | Source | Allowed optional fields | Meaning |
| --- | --- | --- | --- |
| `onboarding_started` | `onboarding` | — | A new onboarding flow was presented |
| `category_selection_completed` | `onboarding` | `count` | Number of predefined categories selected |
| `first_prayer_created` | `onboarding` | `status` | First Pray persisted successfully or failed |
| `prayer_time_selected` | `onboarding` | `status` | Optional time chosen or skipped; never include the time value |
| `notification_permission_requested` | `onboarding` | — | System permission prompt requested after user action |
| `notification_permission_granted` | `system` | `status` | Permission outcome is granted |
| `notification_permission_denied` | `system` | `status` | Permission outcome is denied or restricted |
| `onboarding_completed` | `onboarding` | `status` | Required setup committed, with optional setup outcome |
| `daily_prayer_viewed` | `today` | `count` | Number of eligible categories viewed in a session |
| `daily_prayer_started` | `today` | — | User explicitly began the daily prayer flow |
| `daily_prayer_completed` | `today` | `durationBucket`, `status` | Prayer-day write outcome; success only after persistence |

Widget, revisit, retention, mix, and dashboard event contracts are reserved for issues #50–#55 and are not emitted by this implementation.

## Content explicitly prohibited

Never collect Pray titles/bodies, reflection text or answers, custom category labels, person names, category/Pray identifiers, device advertising identifiers, or stable user identifiers. Do not log event payloads to console or persist them to `PrayData`, backups, or analytics queues.

## Idempotency and correlation

Onboarding milestones are emitted once per installation per milestone using local completion flags containing only the milestone key. A retry after a failed write may report the failure outcome, but must not claim first-Pray success. Daily-prayer correlation, if needed for in-memory ordering, is ephemeral, random, and never enters the event envelope or disk.

## KPI interpretation

The North Star is Weekly Returning Prayer Users. An app open alone is not a prayer return; use a qualifying prayer event. Supporting KPI definitions will be finalized in #52. Analytics opt-out and provider failures must not affect any core flow.
